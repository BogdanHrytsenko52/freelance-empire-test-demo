# Завдання frontend, узгоджене з backend

Документ зводить ТЗ frontend (Артем) із ТЗ backend (тімлід: auth, симуляція, AI; Тьома: моделі, API, тести). Префікс усіх маршрутів — `/api` (`VITE_API_URL`).

## 1. Сторінки та API

| Сторінка | Запити | Поведінка frontend |
|---|---|---|
| `/login` | `POST /auth/token/`, `GET /auth/me/` | Вхід за **username** і паролем. 429 показує «Забагато запитів» (на backend є throttling) |
| `/register` | `POST /auth/register/`, потім `/auth/token/` | Поле `role` не передаємо. Після реєстрації автоматичний вхід і перехід на `/company/create` |
| Вихід | `POST /auth/logout/` з `refresh` | Refresh потрапляє в blacklist, токени очищаються локально |
| `/company/create` | `POST /companies/`, `GET /companies/me/` | 404 на `/companies/me/` означає, що компанії немає, і веде на створення. Друга компанія заборонена, помилку показуємо. Баланс 100 000 ₴ ставить сервер |
| `/dashboard` | `GET /companies/me/`, `/companies/me/finance/`, `/employees/`, `/projects/`, `/transactions/`, `/notifications/` | Окремого ендпоінта дашборда немає, збираємо з кількох запитів. Ігровий день див. п. 4 |
| `/employees` | `GET /employees/`, `/employees/candidates/`, `POST /employees/hire/`, `/employees/{id}/fire/` | Фільтр за спеціалізацією. Звільнення з підтвердженням. Найм вимкнений, якщо баланс від'ємний (борг), остаточно рішення за сервером |
| Призначення | `POST /projects/{id}/assign/`, `/unassign/` | Кнопка «Призначити» у таблиці працівників відкриває вибір проєкту й завдання. API належить проєктам, а не працівникам |
| `/contracts` | `GET /contracts/`, `/contracts/{id}/`, `POST /contracts/{id}/accept/` | Статуси: `available`, `negotiating`, `accepted`, `completed`, `failed`. Після прийняття перехід до створеного проєкту |
| `/contracts/:id/chat` | `GET/POST /contracts/{id}/chat/` | Ліміт довжини повідомлення, ліміт переговорів і запитів (429), резервна відповідь, якщо Groq недоступний. Умови змінює лише сервер, кнопка «Прийняти» викликає `/accept/` |
| `/projects`, `/projects/:id` | `GET /projects/`, `/projects/{id}/`, `POST …/assign/`, `…/unassign/`, `…/submit/` | Kanban без drag-and-drop: статуси `todo` → `in_progress` → `done` та прогрес змінює лише симуляція. Дозволені дії: призначити, зняти, здати. Передчасна здача відхиляється сервером |
| `/events` | `GET /events/`, `/events/history/`, `POST /events/{id}/choose/` | Не більше 2 активних. Після вибору кнопки блокуються (рішення застосовується один раз), показуємо наслідки |
| `/finance` | `GET /transactions/` (фільтр за типом), `GET /companies/me/finance/` | Графіки за `game_day` (Recharts). Суми приходять рядками |
| `/leaderboard` | `GET /leaderboard/` | Сортування й пагінація. «Капітал» на UI = `balance`. Власну компанію підсвічуємо за `company_id` |
| `/profile` | `GET /auth/me/`, `PATCH /companies/me/`, `POST /auth/logout/` | «Дозволені налаштування» = лише назва компанії. `balance`, `reputation`, `level` змінити не можна. Роль лише відображається |
| Сповіщення | `GET /notifications/`, `POST /notifications/{id}/read/` | Список на дашборді, позначка «прочитано» |

## 2. Що змінилося відносно початкового ТЗ frontend

1. Вхід за `username`, а не за email (стандартна поведінка SimpleJWT).
2. Маршрути авторизації: `/auth/token/`, `/auth/token/refresh/`, `/auth/logout/`, `/auth/me/`.
3. Спеціалізація «Design» називається **Designer**.
4. Ролі: Guest (без токена), Player, Moderator, Admin. Окремих сторінок для модератора й адміністратора в ТЗ немає, роль показуємо в профілі.
5. Kanban тільки для читання: ручно переміщувати картки або ставити 100% не можна.
6. Сума завжди рядок (`DecimalField`). Фінансових розрахунків на клієнті немає, лише форматування (`utils/money.ts`).
7. Баланс може бути від'ємним: показуємо червоним і блокуємо найм.
8. Поточний гравець без компанії потрапляє на `/company/create` з будь-якої ігрової сторінки (`CompanyGate`).
9. Симуляція працює офлайн (1 реальна година = 1 ігровий день), тому дані на сторінках оновлюємо при поверненні у вкладку й за таймером.
10. Помилки: показуємо `detail` / `non_field_errors`, помилки полів DRF підсвічуємо біля полів, окремі тексти для 429, 5xx і недоступного сервера.
11. CORS: dev-адреса frontend — `http://localhost:5173`, її треба додати в налаштування backend.

## 3. Токени

- `access` і `refresh` зберігаються в `localStorage`.
- Доступ автоматично оновлюється через `/auth/token/refresh/` при 401, паралельні запити чекають на один refresh.
- Якщо на backend увімкнено `ROTATE_REFRESH_TOKENS`, новий `refresh` зберігається автоматично.
- Якщо оновити токен не вдалося, користувача розлогінює і веде на `/login`.

## 4. Відкриті питання до тімліда й Тьоми

1. **Поточний ігровий день і дані симуляції для Dashboard**: у ТЗ backend є лише вимога «надати Артему», а ендпоінта немає (наприклад, `GET /api/game/state/`).
2. **Єдиний формат помилок**: чи залишається стандартний DRF (`detail` або `{поле: [текст]}`)?
3. **Роль**: значення у `/auth/me/` (`player` / `moderator` / `admin`?).
4. **Імена полів і значення enum**: у `src/types/game.ts` лише пропозиція. Найкраще дати Swagger (drf-spectacular), тоді типи генеруються з OpenAPI.
5. **Тіла запитів**: `hire` (id кандидата), `assign` / `unassign` (працівник + завдання), `choose` (id рішення), `chat` (текст).
6. **Чат**: формат `ChatMessage`, чи повертається поточна пропозиція (бюджет, дедлайн), скільки переговорів лишилося, ознака резервної відповіді (fallback).
7. **Відповідь `/projects/{id}/submit/`**: результат (прийнято / доопрацювання), виплата, зміна репутації; статуси проєкту.
8. **Відповідь `/events/{id}/choose/`**: як показати наслідки.
9. **Дедлайни**: це номер ігрового дня чи дата?
10. **Лідерборд**: параметри сортування й пагінації, ознака власної компанії.
11. **Пагінація**: які списки пагіновані.
12. **Суми**: підтвердити, що витрати від'ємні, чи тип визначається лише полем `type`.

## 5. Режим мок-даних

Поки backend не готовий, frontend працює на мок-даних (дозволено ТЗ). Режим вмикається в `frontend/.env`:

```env
VITE_USE_MOCKS=true    # мок-дані, backend не потрібен
VITE_USE_MOCKS=false   # справжній Django API
```

- Мок підміняє лише транспорт Axios (`src/mock/adapter.ts`). Весь код сторінок і `*Api.ts` однаковий для моків і справжнього backend, тому перехід на реальний API не потребує змін у сторінках.
- Мок-сервер відтворює правила з ТЗ backend: один гравець і одна компанія, найм заборонений при боргу, перевірка спеціалізації при призначенні, зарплата = місячна / 30, штраф за прострочення 2% на день (максимум 30%), івенти (шанс 15%, максимум 2 активні, вибір один раз), переговори з лімітами, рейтинг із пагінацією.
- Гроші в моку рахуються в копійках (цілі числа).
- В моку 1 ігровий день = 10 секунд (`src/mock/ticker.ts`), щоб було видно прогрес Kanban. У грі 1 реальна година = 1 день.
- Стан моків зберігається в `localStorage` (`fe_mock_db_v1`). Нова реєстрація починає гру з нуля. Щоб скинути стан вручну, видаліть цей ключ.
- Для входу в моку спершу зареєструйтесь: логін працює лише для створеного акаунта (як і на справжньому backend).

| Що | Припущення |
|---|---|

| Пагінація рейтингу | `?page=N&ordering=reputation\|balance\|completed_contracts`, відповідь `{count, next, previous, results}` |
| Фільтри | `GET /employees/?specialization=`, `/employees/candidates/?specialization=`, `/transactions/?type=` |
| `POST /contracts/{id}/accept/` | відповідь `{ "project_id": 1 }` |

## 7. Стан backend за репозиторієм (звірка з кодом)

**Реалізовано:** `POST /api/auth/register/`, `/token/`, `/token/refresh/`, `/logout/`, `GET /api/auth/me/`, документація схеми `/api/schema/`.

**Ще немає HTTP API** (застосунки Тьоми не злиті, а `simulation/` та `ai_service/` поки лише сервіси без маршрутів): компанії, працівники, контракти, проєкти, транзакції, івенти, сповіщення, рейтинг, ігровий день, чат `/contracts/{id}/chat/`. Для цих розділів frontend працює на моках.

### Що з'ясувалось і вже враховано
- Реєстрація вимагає **`password_confirm`**. Раніше frontend його не надсилав, тому реальний backend відповів би 400. Виправлено; помилку поля `password_confirm` форма показує біля поля підтвердження.
- Вхід: `username` + `password`. Відповідь: `{access, refresh, user}`.
- Паролі перевіряє Django (мінімальна довжина, поширені паролі, лише цифри, схожість на username/email). Помилки приходять у `password: [...]`.
- Обмеження частоти: вхід 5/хв, реєстрація 3/хв, оновлення токена 10/хв. Frontend показує повідомлення про 429.
- Токени: access 15 хв, refresh 7 днів, **ротація refresh увімкнена** з blacklist. Клієнт зберігає новий `refresh` після кожного оновлення.
- CORS уже дозволяє `http://localhost:5173` та `http://127.0.0.1:5173`.
- AI: ліміт повідомлення 1000 символів, 5 запитів/хв, до 10 повідомлень у переговорах, є резервна відповідь `fallback_reply`.
- Моки: `VITE_USE_MOCKS=hybrid` вмикає **реальну авторизацію + моки решти**. Дані моків спільні для всіх акаунтів у браузері.

### Що треба від backend для чату й гри (відкриті питання)
1. Ендпоінти ігрового дня й чату (формат у розділі 6). У `ai_service` відповідь NPC має `message`, `action`, `budget`, `deadline`, тож `proposal` у чаті відповідає цьому.
2. У backend ліміт рахується в **повідомленнях** (10), а не в «переговорах». Узгодити поле `negotiations_left`.
3. Помилка ліміту AI зараз `ValueError`: потрібен HTTP 429 з текстом, щоб frontend показав зрозуміле повідомлення.
